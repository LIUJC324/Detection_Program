# 2026-04-15 i-predictor 运动预测系统规划

## 目标重述

预想项目 `基于时空特征融合演进算法的 i-predictor 运动预测系统`，如果要基于当前 `rgbt_uav_detection` 仓库尽快推进，建议不要直接把现有检测模型硬改成“端到端轨迹预测器”，但也不能退化成“只有检测 + 卡尔曼”的普通方案。

更合适的落地方式是：

1. 先把 `检测` 做成稳定的 `目标状态观测器`
2. 尽快补上 `轨迹历史缓存`
3. 从第一版开始就引入 `时空融合预测器`
4. 同时加入 `演进 / 自适应权重` 机制

这样做的核心原因是：当前仓库已经有较完整的多模态检测和流式服务底座，但几乎没有真正的时序建模、轨迹关联和未来轨迹监督数据。  
所以正确路线不是放弃“时空融合演进算法”，而是先用现有工程底座，把这个算法做成一个轻量可训练、可演示、可逐步增强的预测主干。

## 当前仓库能直接复用的部分

### 1. 多模态检测模型底座已存在

当前主线模型已经具备：

- `RGB + Thermal` 双模态输入
- 双分支 backbone
- 跨模态融合模块
- neck + head + detector 装配

对应代码：

- `model/detector.py`
- `model/network/backbone.py`
- `model/network/fusion_module.py`

这部分最大的价值不是“它已经是预测模型”，而是：

1. 已经能产生每帧目标框和类别
2. 已经把多模态特征融合这件事跑通
3. 后续可以把检测结果转成时序状态序列

### 2. 数据读取和训练脚手架是完整的

当前训练侧已经有：

- 配置化训练入口 `scripts/train.py`
- 成对 RGB/T 数据集读取 `data/dataset.py`
- 数据增强与预处理
- 评估、导出、可视化

这意味着后续做序列数据集时，不需要从零写训练基础设施，只需要把“单帧样本”扩成“历史窗口样本”。

### 3. 在线服务和视频流会话能力已存在

当前服务侧已经具备：

- FastAPI 推理接口
- 视频/流读取
- 会话管理
- 抽帧调度
- 回调机制

对应代码：

- `service/api/app.py`
- `service/core/predictor.py`
- `service/streaming/session_manager.py`

这对 i-predictor 很关键，因为运动预测最终大概率要做成：

1. 输入实时流
2. 输出连续状态
3. 输出下一时刻或未来若干时刻预测

当前仓库已经把这条工程链路的一大半铺好了。

### 4. 检测路线已经在向更标准的几何语义演进

仓库里已经有 `YOLO-OBB` 迁移准备和训练脚本：

- `scripts/train_yolo_obb.py`
- `docs/changes/20260412_yolo_obb_migration_plan/README.md`

这说明项目已经开始从“水平框检测”往“更稳定的几何状态表达”演进。  
对未来运动预测来说，目标中心点、速度方向、朝向角度都是更好的状态变量。

## 当前缺口

如果直接拿当前仓库去做 i-predictor，主要缺 5 件事：

### 1. 缺多目标跟踪

现在只有逐帧检测，没有稳定的：

- `track_id`
- 轨迹生命周期管理
- 遮挡恢复
- 轨迹平滑

没有跟踪，就没有连续轨迹，也就谈不上未来运动预测。

### 2. 缺序列样本定义

现在 `data/dataset.py` 读的是单帧图像对 + 单帧框标注。  
运动预测至少需要：

- 历史 `N` 帧状态
- 未来 `K` 帧真值
- 可选场景上下文
- 可选模态质量信息

### 3. 缺预测标签和评估口径

当前指标都是检测指标。  
预测任务还需要重新定义：

- 预测对象：中心点、速度、朝向、轨迹点，还是占用区域
- 预测时域：`0.5s / 1s / 2s`
- 评价指标：`ADE / FDE / Miss Rate / ID switch / latency`

### 4. 缺时序模型

当前仓库只有轻量时序展示平滑，没有真正的：

- RNN/LSTM/GRU 序列编码
- Transformer 时序建模
- 图结构交互建模
- 物理约束或运动学约束

### 5. 缺“比赛亮点”和“最小可演示版”的拆分

这是目前最容易拖慢进度的地方。  
如果一开始就追求“时空特征融合演进算法 + 多模态 + 多目标交互 + 预测 + 可视化 + 部署”，项目会直接失控。

## 推荐总路线

## Phase 1：先做必须带“时空融合演进算法”的 baseline

目标：`两周内拿到能演示的 i-predictor v0`

推荐结构：

1. 检测器：
   - 继续用当前较稳的一条检测线
   - 以 `RGB-T FCOS` 或 `RGB-only YOLO-OBB` 作为观测源
2. 跟踪器：
   - 先用经典 tracking-by-detection 思路
   - 输出 `track_id + center + bbox/obb + timestamp`
3. 时空融合预测器：
   - 输入 `历史运动状态 + 当前局部场景特征 + 模态质量特征`
   - 预测未来 `5~10` 个点
4. 演进模块：
   - 根据模态质量、目标速度变化、最近预测误差
   - 动态调整不同分支权重
4. 演示：
   - 在视频上同时画出当前框、轨迹尾迹、未来轨迹

这条路线的优点：

1. 最快出结果
2. 最容易定位问题
3. 最适合比赛前期抢进度
4. 后面所有更强模型都可以拿它当 baseline

这一阶段的关键要求是：

1. 第一版就必须有 `时序历史编码`
2. 第一版就必须有 `场景/模态信息融合`
3. 第一版就必须有 `自适应权重更新`

也就是说，v0 就要满足“时空融合演进算法”的命名逻辑，只是先做轻量版，而不是终极版。

## Phase 2：把 baseline 升级成真正的学习式预测

目标：`第 3~4 周形成可训练、可对比、可写材料的 i-predictor v1`

建议输入定义为三类特征：

1. 目标历史运动特征
   - 中心点序列
   - 宽高/朝向变化
   - 速度、加速度
2. 场景观测特征
   - 目标邻域图像 patch
   - 全局低分辨率场景图
   - 可选道路/车道先验
3. 模态质量特征
   - RGB 亮度
   - Thermal 对比度
   - 检测置信度
   - 融合质量分数

推荐最先做的学习式结构：

1. `运动分支`
   - `GRU/LSTM` 编码历史状态
2. `场景分支`
   - 轻量 CNN 编码目标周边 patch
3. `质量分支`
   - MLP 编码模态质量和检测置信度
4. `融合层`
   - 门控融合或交叉注意力
5. `预测头`
   - 直接回归未来轨迹点

这个版本已经能比较自然地对应“时空特征融合”，同时也为“演进”留出接口。

## Phase 3：把“演进算法”做成明确主线

目标：`做出区别于普通 LSTM predictor 的比赛亮点`

“演进”不建议机械理解成必须上复杂的遗传算法或大规模神经架构搜索。  
更务实、也更适合比赛落地的定义是：让系统能根据场景质量、目标类型、历史机动性和最近预测误差，自适应地切换或重加权预测分支。

推荐做法：

1. 做 `双预测头`
   - 头 A：短时稳定预测
   - 头 B：机动性更强的变化预测
2. 做 `质量感知门控`
   - 夜间或低照时提高 thermal 相关特征权重
   - 快速运动时提高历史动力学分支权重
3. 做 `在线误差反馈`
   - 根据最近几帧预测误差动态调整分支权重

这样就能把“演进算法”解释成：

- 预测器结构会随场景和历史误差自适应演进
- 融合权重会随模态可靠性变化
- 预测策略不是固定单一路径

如果比赛题目或项目答辩必须更强调“演进”两个字，可以再补一层离线演进机制：

1. 在训练阶段维护多个候选融合策略
2. 用验证集误差选择更优门控参数或分支组合
3. 把选优后的策略固化到在线模型

这样既保留“演进”概念，又不会把项目复杂度直接拉爆。

这比一开始直接上重型进化优化更容易落地，也更适合比赛叙事。

## 最快推进方案

如果目标是“尽快完成一些新项目进度”，建议严格按下面顺序做。

### 第 1 优先级：先拿到连续轨迹

本周必须先完成：

1. 在流式推理结果里增加 `track_id`
2. 为每个目标缓存最近 `N` 帧状态
3. 输出 `center_x, center_y, velocity_x, velocity_y`
4. 在回调结果中增加 `future_points`

没有这一步，后面所有预测模型都没有可靠输入。

### 第 2 优先级：快速形成可视化 demo

建议新增一个最小演示链路：

1. 输入视频/流
2. 输出检测框
3. 输出轨迹尾迹
4. 输出未来 `1s` 预测点

只要这个 demo 出来，项目就从“想法”变成“有系统雏形”。

### 第 3 优先级：补序列训练数据

建议新增数据中间格式，例如：

- `sample_id`
- `track_id`
- `history_states`
- `future_states`
- `rgb_patch_paths`
- `thermal_patch_paths`
- `scene_meta`

把它们保存成：

- `jsonl`
- 或 `npz / pt`

这一步做完后，学习式预测模型就能正式开训。

### 第 4 优先级：做一个很强但很轻的第一版时空融合演进模型

建议第一版优先做：

- `GRU/LSTM + 场景 patch CNN + 质量分支 MLP + 自适应门控融合`

原因：

1. 训练更稳
2. 对数据量要求更低
3. 更容易解释
4. 更容易和去掉“演进模块”的版本做 ablation

### 第 5 优先级：最后再补论文包装和高级模块

比赛/项目材料里的亮点建议按这个顺序叙述：

1. 多模态观测
2. 连续轨迹恢复
3. 时空特征融合预测
4. 质量感知自适应演进
5. 在线服务化演示

不要反过来先讲复杂算法，再补工程闭环。

## i-predictor 最小算法形态

如果必须明确体现“时空融合演进算法”，建议第一版直接定义成下面这个结构：

1. `Temporal Encoder`
   - 输入：目标最近 `N` 帧中心点、速度、框尺度、朝向
   - 作用：提取运动趋势
2. `Spatial Encoder`
   - 输入：目标周围 `RGB/T` patch 或低分辨率全局场景
   - 作用：提取局部环境和邻域影响
3. `Modal Quality Encoder`
   - 输入：亮度、热红外对比度、检测置信度、遮挡程度
   - 作用：估计当前观测可靠性
4. `Evolution Gate`
   - 输入：时序特征、空间特征、质量特征、最近误差
   - 作用：动态输出各分支融合权重
5. `Prediction Head`
   - 输出：未来轨迹点、未来速度或不确定度

这个定义有 3 个优点：

1. 名称和题目高度一致
2. 很容易从现仓库拆分实现
3. 后续能自然升级到 Transformer 或图网络

## 推荐里程碑

### M1：3 天内

- 跑通检测结果到轨迹缓存
- 能输出 `track_id`
- 能画尾迹

### M2：7 天内

- 跑通常速度/卡尔曼预测
- 视频 demo 能展示未来点
- 服务接口能回传预测结果

### M3：14 天内

- 形成序列训练集
- 跑通 `LSTM/GRU predictor`
- 给出首轮 `ADE/FDE` 对比

### M4：21~28 天

- 加入模态质量感知融合
- 做自适应权重或双头预测
- 固化比赛材料和方法图

## 当前最值得坚持的原则

1. 先把 `检测系统` 变成 `时序观测系统`
2. 先做 `轻量但完整的时空融合演进 baseline`，不要一开始就做大而全
3. 先拿到 `连续轨迹和演示视频`，再追求复杂模型
4. 未来项目的创新点，要建立在现有工程底座之上，而不是推倒重来

## 一句话结论

当前仓库最适合的演进方向是：

`多模态检测底座 -> 多目标跟踪 -> 时空融合预测器 -> 演进门控/自适应机制 -> 完整 i-predictor 系统`

也就是说，`时空融合演进算法` 不是最后再补的装饰，而应该从第一版起就是系统主干。
